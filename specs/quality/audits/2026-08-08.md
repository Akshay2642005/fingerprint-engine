## Confirmed bugs

### BUG-001 — Browser SDK swaps `schema_version` / `feature_count` in the worker reply (high)

`src/engine/ops/hash.zig` writes `[32]digest | u16 feature_count | u16 schema_version`,
but `src/clients/browser/src/transport.ts` (`parseWorkerReply`) reads schema at
33..35 and count at 35..37 — swapped. The TS test encodes the same wrong
layout, so the suite is green while the SDK reports wrong metadata for every
successful reply. **First to fix** — it is user-visible and silent.

### BUG-002 — Version drift (medium)

`worker version` → `0.2.0`; AMQP `product_version` → `0.2.0`;
`wasm.zig` `sdk_version` → `0.1.0`; release is `0.2.2`. Six copy-pasted
version constants, no single source of truth. Fix with injected build
options (see F-3).

### BUG-003 — Stale spec test counts (low)

`specs/planning/SESSION.yaml` says 382/376/6; the suite is 383/376/7.

## Hardening gaps

### H-1 — No socket idle timeout on the worker TCP transport (medium/high)

`src/adapter/tcp.zig` reads frames with `readNoEof` and no `SO_RCVTIMEO`.
A client that connects and sends fewer than 48 bytes, then goes silent,
**wedges the worker's accept loop forever** (single-client design). The AMQP
client already applies receive deadlines; the TCP transport should too
(e.g. `std.posix.setsockopt` `SO_RCVTIMEO` on the accepted socket, close on
timeout). The ingress is a trusted speaker today, but any exposed worker port
becomes remotely wedge-able without this.

### H-2 — No graceful shutdown (medium)

The worker dies on SIGTERM/SIGINT mid-request (tini forwards the signal).
For orchestrated rollouts the process should stop accepting, drain in-flight
requests, then exit. Ingress needs the same once it exists.

### H-3 — No health/liveness probe (medium)

`deploy/Dockerfile.worker` has no `HEALTHCHECK` and the worker exposes no
probe. Orchestrators (k8s/Docker swarm) cannot distinguish "starting" from
"dead". The ingress should expose `GET /healthz`; the worker TCP transport
should answer a dedicated health frame type (or the ingress pool probes
connections as its liveness signal).

### H-4 — Ingress security posture (medium, applies once the ingress exists)

- **Auth**: both the ingress HTTP path and the worker FPKG TCP endpoint are
  unauthenticated today. Decide: network ACL / mTLS for worker→ingress,
  optional API key on the HTTP ingress.
- **Rate limiting**: the ingress is the only public surface; needs per-client
  limits before production exposure.
- **TLS**: termination at the ingress or a reverse proxy.

### H-5 — Oversized-body handling (low/medium)

The FPKG layer caps payloads at 16 MiB (`adapter/transport.zig max_payload`)
— fine for the worker — but the ingress must reject oversized HTTP bodies
via `Content-Length` *before* proxying (413), with a configurable cap well
below 16 MiB (a real SignalPackage with canvas/audio bytes is tens of KB).

## Required features

### F-1 — HTTP ingress (`src/ingress/`) — the next milestone

The planned M5. Design in `specs/architecture/ingress.md`. Includes the ingress
Dockerfile, `zig build docker:ingress`, compose services, CI jobs, and e2e
tests. This is the component the browser SDK's `configure({ ingressUrl })`
already targets (default `http://127.0.0.1:8080`), so nothing in the SDK
changes — the ingress just needs to exist.

### F-2 — Application logging

Today: `std.debug.print` in the worker/scripts mixed with
`std.log.scoped(.amqp)` in the AMQP client — no levels, no scopes, no way to
silence, no structured output. Design in `specs/architecture/logging.md`: a leaf
`src/log.zig`, `--log-level` on every executable, `--quiet` on `amqp get`,
optional JSON output.

### F-3 — Version single source of truth

Prerequisite for fixing BUG-002. Inject `build.zig package_version` through
`b.addOptions()` into every module that needs it; delete the six hardcoded
constants.

### F-4 — AMQP consumer + dead-letter queue

The AMQP client supports polling `basic.get` only. The fraud platform (Go)
will consume results, but the Zig side still needs: push consumption
(`basic.consume` + QoS) for any worker↔broker command/control, and a DLQ for
poison frames and failed publishes (the worker currently logs-and-drops:
`--publish` failures and `mandatory=false` unroutable messages vanish). Add
a consumer e2e test that runs against a live broker and skips cleanly when
none is reachable (compose provides one).

### F-5 — Full-stack local compose

`compose.yml` only runs RabbitMQ. Add `worker` (with `--publish=amqp`) and
`ingress` services so `docker compose up` gives a working browser→ingress→
worker→broker loop locally.

### F-6 — Release pipeline surface

`release.yml` release notes + GHCR push cover only the worker image. When
the ingress ships, publish `fingerprint-ingress` to GHCR the same way and
list it in the release notes. Keep `publish-npm` idempotent as-is.
