# Platform ledger — reference persistence for collection events

The Fingerprint Engine is compute-only: it never owns a database (D-v1-4). This
directory contains the **platform-side** persistence contract for the one
durable document the engine emits per collection — the ADR-013
`collection_event` envelope. There is no engine code here and no engine
dependency on a database; the files are DDL/validator plus fixtures that your
platform repo can copy and own.

- Envelope contract: [`specs/decisions/0013-event-envelope-ledger-adr.md`](../../specs/decisions/0013-event-envelope-ledger-adr.md)
- Postgres DDL: [`postgres/schema.sql`](postgres/schema.sql)
- MongoDB validator + indexes: [`mongodb/collection_events.js`](mongodb/collection_events.js)
- Example envelope: [`../../tests/fixtures/ledger/collection-event-v2.json`](../../tests/fixtures/ledger/collection-event-v2.json)

## What arrives on the wire

With `worker start --publish=amqp`, every successful collection publishes one
extra message **after** the unchanged `fingerprint_result` reply:

| Property | Value |
| --- | --- |
| Exchange | `fingerprint` (direct, durable) |
| Routing key | `result.collection-event` |
| Header `fpkg-message-type` | `10` (`collection_event`) |
| Header `fpkg-envelope-version` | `1` |
| Body | the **complete FPKG frame** (`magic "FPKG"` + 48-byte header + payload) |
| Payload | the ADR-013 JSON document, UTF-8, keys in a frozen order |

The reply/ledger fanout is at-least-once and best-effort: an envelope that
fails to build (over the 64 KiB cap) or publish is logged and dropped, and the
live `result.*` reply fanout remains the fallback. The consumer must therefore
be idempotent, not assume a complete stream.

### 1. Strip the frame header

The body is not a bare JSON document. Parse the 48-byte FPKG header
(`src/io/frame.zig`), verify `magic == "FPKG"`, `version == 1`, and
`payload_len` matches the remaining bytes, then parse `payload` as JSON. The
header also carries the payload's SHA-256 integrity digest; verify it before
inserting so a corrupt message is dead-lettered rather than stored.

If your consumer uses a broker-side header instead, prefer
`fpkg-message-type == 10` to route, but still frame-parse the body — the header
is the authoritative type.

### 2. Convert timestamps

`collected_at` and `ingress_received_at` are epoch **milliseconds** (integers).
Convert at ingest:

```sql
to_timestamp(collected_at_ms / 1000.0),
CASE WHEN ingress_received_at_ms = 0 THEN NULL
     ELSE to_timestamp(ingress_received_at_ms / 1000.0) END
```

`ingress_received_at = 0` means the collection did **not** traverse the HTTP
ingress (a direct TCP/loopback client), so store `NULL`, never 1970.

### 3. Insert idempotently

`package_id` is the SDK-minted 128-bit per-collection id (32 lowercase hex
characters) and is the sole idempotency key. Retries and broker redelivery of
the same collection collide on it instead of duplicating a row.

Postgres:

```sql
INSERT INTO collection_events (...)
VALUES (...)
ON CONFLICT (package_id) DO NOTHING;
```

MongoDB: the unique index on `package_id` rejects the duplicate; treat error
code `11000` as success.

Any other parse/schema failure is not retryable — dead-letter it.

## Field notes

- `fingerprint_id` — full SHA-256 over the canonicalized signals (the value the
  SDK receives), 32 bytes. Indexed for continuity lookups.
- `core_digest` / `core_feature_count` / `core_version` — the stable-core gate
  (D-v1-5). `core_version` identifies the subset revision; a different value
  means the digests are **not** comparable across rows. Never treat a matching
  `core_digest` alone as a verdict.
- `signals` — canonicalized feature values keyed by registry feature name.
  Names are stable once published (ADR-012); a name is never reused for a
  different feature.
- `risk` — `{score, label, flags}` from the engine's risk op. `status` is the
  engine `Status.code()` and is `0` (`ok`) for every emitted envelope; a
  non-zero status is not expected on this topic and should be treated as a
  producer bug.

## Privacy

`signals` contains device-identifying values, including high-entropy and
sensitive features (user agent, canvas/WebGL strings, fonts, screen metrics).
This is the payload's purpose, so:

- encrypt at rest (platform-managed keys, e.g. `pgcrypto`/AES-GCM or the managed
  equivalent) and restrict the raw column/field to an authenticated service;
- never expose raw `signals` to unauthenticated callers — read through your
  access-controlled API;
- apply your retention policy to `collected_at`; the engine has none;
- `session_id` is a tenant-provided correlation label (1–128 bytes of
  `[A-Za-z0-9._:-]`, empty when absent). Treat it as an opaque tenant value; the
  engine never logs its contents.

## Fixture

`tests/fixtures/ledger/collection-event-v2.json` is generated by the production
encoder from the canonical `signal-package-v2.bin` fixture through the real
worker reply path (`tests/ledger/ledger_fixture_test.zig`), so it cannot drift
from the encoder. Use it to test your consumer/ingestion code. Regenerate after
an intentional contract change with:

```sh
SNAP_UPDATE=1 zig build test
```

Because keys are emitted in a frozen order and the document is a pure function
of the package, the same collection always produces byte-identical JSON.
